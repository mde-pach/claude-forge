Forge does not add a lifecycle of its own. It plugs pieces into Claude Code's hook events, plus `forge apply` before the session and git and CI after it. The schema below is Claude Code's lifecycle with every Forge piece attached; grey filled pieces always run, dashed ones run when a rule needs them. Every rule and pack page shows this same schema with only its own pieces lit up.

<LifecycleSchema variant="overview" events={[]} />

Forge acts at seven moments. These pages explain each one and carry its tests.

| Step | What runs | What it can do |
|---|---|---|
| [**forge apply**](./apply/) | you run `forge apply` (and `forge status`) | detects packs, writes the setup, **audits** your tool configs |
| [**Session start**](./session/#session-start) | SessionStart hook | **informs** Claude: branch, changes, packs, missing tools; context files |
| [**Tool call**](./session/#tool-call) | Claude Code permissions and sandbox; PreToolUse guard | **blocks** or **asks** before a Bash command, a read or an edit |
| [**After an edit**](./session/#after-an-edit) | PostToolUse hooks | **fixes** formatting, **tells Claude** lint and ast-grep findings, **wakes Claude** on type errors |
| [**Claude stops**](./stop/) | UserPromptSubmit snapshots the tree; Stop hook → `check.sh` on what the turn changed | **blocks** the stop until the change passes; hands over after 3 tries |
| [**git commit**](./commit-ci/#pre-commit) | pre-commit hook → `check.sh --changed` | **blocks** the commit |
| [**CI**](./commit-ci/#ci) | `check.sh --since <base>` on a pull request, `--all` on the default branch | **blocks** the build: what the branch added, or the whole project |
