title: Configuration
description: Adjust detected packs and rules with forge.yaml, local packs and local rules.

Most projects need no configuration: Forge activates packs from your manifests, lock files and sources. Three optional inputs adjust the result. Forge never rewrites them, and Claude must ask before editing them.

## `forge.yaml`

```yaml
packs:
  add: [typescript/zod]           # activate a pack (and its ancestors)
  remove: [typescript/playwright] # deactivate a pack and its sub-packs
disable:
  - id: python/pytest/run
    reason: The suite needs a GPU; it runs in CI only.
accept:                           # a config change the ratchet reported, made on purpose
  - rule: typescript/config-ratchet
    change: "biome.json: linter.rules.suspicious.noExplicitAny error -> warn"
    reason: Migrating the legacy API client; back to error by Q3.
```

A rule you don't want is disabled with a reason.

`accept` answers the config ratchet (`python/config-ratchet`, `typescript/config-ratchet`): when a tool config is loosened (a lint rule lowered, a strict flag removed, a path excluded, a coverage threshold lowered), the check fails at Stop, at pre-commit and in CI with one line per setting. Copying that line into `accept` with a reason records the change as deliberate. The file format is in [Schemas](../../reference/schemas/#forge).

## File roles

Rules name the files they are about by role (`@python-tests`, `@alembic-migrations`, `@dockerfile`, …), never by globs of their own. A role starts from Forge's defaults, which the tool's own config replaces when Forge can read it as data: pytest's `testpaths` and `python_files`, `alembic.ini`'s `script_location`, `schema.prisma`'s generator `output`. Code configs (`vitest.config.ts`, …) are never run, so a layout they set goes in `forge.yaml`:

```yaml
files:
  python-tests: {add: ["integration/**/check_*.py"]}   # added to the role
  e2e-tests: {set: ["apps/web/e2e/**"]}                # replaces the defaults and the tool's config
  typeorm-datasource: {set: [src/data-source.ts]}      # a role with no default
```

`forge status` lists each role the active rules use, its patterns and where each comes from, and says when one matches no file; a rule whose role has no pattern is reported as not enforced rather than run on other files.

## Local packs and rules

- `.forge/packs/<id>/` holds a pack in the same layout as the built-in ones (`pack.yaml`, `rules/*.yaml`). See [Writing packs](../../contributing/writing-packs/).
- `.forge/rules/*.yaml` holds standalone rules in the same format. A local rule whose `id` equals a pack rule's id replaces it; a new id adds a rule.

Rules have no parameters; a local rule of the same id is how you adapt one: copy the rule from its pack page into `.forge/rules/<name>.yaml` and change it, for example add `"!path/to/file.ts"` to `scope.files` to exempt a file. `claude-forge packs lint --repo .` reports the content lints on your local packs and rules.

## YAML

Pack files, rule files and `forge.yaml` are read with a strict YAML parser: no anchors, aliases or tags, and duplicate keys are rejected.
